# Задача: снизить трафик к базе данных backend-api

## Контекст
Проект: канбан-доска для Telegram Mini App. Backend — `backend-api/src/server.js` (чистый Node.js `http`, без фреймворка). Хранилище — `backend-api/src/dataRepository.js`, там несколько реализаций (`createJsonDataRepository`, `createSqliteDataRepository`, `createPostgresDataRepository`) с одинаковым интерфейсом `{ read(): Promise<db>, write(db): Promise<void> }`.

## Проблема
Вся база хранится как **один JSON-объект** (`db`), сериализованный целиком в одну строку/файл БД. `readJson()` в `server.js` вызывается **на каждый HTTP-запрос** (см. `handle(req, res)`, строка с `const db = await readJson();`), и точно так же `writeJson(db)` пишет **весь объект целиком** при любом изменении (создание задачи, перемещение колонки, сохранение страницы и т.д.).

Из-за этого каждый клик пользователя гоняет туда-обратно полный объём данных проекта. На Postgres (Neon, бесплатный тариф) это уже привело к исчерпанию квоты трафика (5 ГБ/мес). При переносе на собственный сервер эта же схема будет напрасно нагружать диск/CPU/сеть и деградировать по мере роста данных.

## Что нужно сделать

1. **Кэшировать `db` в памяти процесса.** При старте — прочитать один раз. Дальше все запросы читают из кэша в памяти (`let cachedDb`), а не дёргают БД на каждый GET.

2. **Debounce записи.** Вместо немедленного `write(db)` при каждом изменении — помечать кэш «грязным» и сбрасывать в БД не чаще, например, раз в 2–3 секунды (`setTimeout`/таймер с накоплением изменений), либо сразу но не блокируя ответ пользователю (fire-and-forget с debounce). Нужно гарантировать, что при сбое процесса теряется максимум последние несколько секунд изменений — это приемлемо.

3. **Не терять данные при остановке процесса.** На `SIGTERM`/`SIGINT` (Render посылает их перед остановкой) — принудительно сделать финальный `write(db)` перед выходом, если есть несохранённые изменения.

4. **Не усложнять бизнes-логику.** Все текущие эндпоинты в `server.js` вызывают `readJson()`/`writeJson()` — сохрани сигнатуры этих двух функций такими же, просто поменяй их внутреннюю реализацию на работу с кэшем + debounce. Обработчики роутов трогать не нужно.

5. Не переусложняй: не нужно резать `db` на отдельные таблицы/эндпоинты — правки должны остаться в пределах `readJson()`/`writeJson()` и, если нужно, `dataRepository.js`.

## Файлы для правки
- `backend-api/src/server.js` — функции `readJson()` и `writeJson()` (около начала файла, до `handle()`)
- `backend-api/src/dataRepository.js` — при необходимости, если нужно добавить метод debounced-записи в репозиторий

## Проверка перед сдачей
- `node --check backend-api/src/server.js` (или запусти `npm run dev` в `backend-api` и убедись что стартует без ошибок)
- Не менять внешние HTTP-контракты (пути, форматы ответов) — только внутренний механизм чтения/записи БД
- Не коммитить и не пушить — просто внеси изменения в рабочую копию, я сам проверю и задеплою
